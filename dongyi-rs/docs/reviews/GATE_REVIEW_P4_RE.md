## 3. 事务一致性、原反例及自身广播

`SharedCfg` 在 lib.rs:24–25 定义；get_config:31–33 读同一锁。save_config_paths:68–83 与 orchestrator.rs:1033–1059 的 on_kind_provider 都在同一锁内基于当前配置创建候选，成功写盘才发布；core/src/lib.rs:155–162 执行保存。空路径或保存错误在发布前返回。provider_for（orchestrator.rs:133–142）继续以非空 kind override 优先，缺失/空串跟随全局；kind 事务发布/拒绝后 :1063–1070 读取当前生效 provider 广播，未引入 LLM 取消。

两类上轮反例的定点推理：

1. 全局由 ollama 改 openai，input/chat override 缺失或空串：成功空 kind 广播进入 loadCfg，:196–199 依据新全局映射两 chip，同时刷新模型和 key。原“弹窗保持旧 chip”的事件处理缺口已修。
2. 设置页先持有旧快照，popup 后来成功写 input=openai，设置页只改 theme：发送的 entries 仅含 theme；后端在锁内 clone 最新配置再写 theme，input override 和其他未编辑字段仍在。两种写入顺序均保留未编辑字段，原“旧快照整份覆盖”已修。此结论限于当前受控表单的叶子路径，不意味着任意父对象替换都能保留其子字段。

设置窗自身也接收 config:updated。监听只提示或 get_config，不再调用 save，因此**无保存广播回环**。但 dirtyRef 仅在渲染时赋值（App.tsx:949）；事件可能在保存 Promise 成功处理前到达，此时仍视为 dirty，出现“其他窗口更新”提示。事件在 clean 时到达则会启动重拉，而 :963–967 返回时只查 disposed，不复核 dirty/patchSeq；因此**无回环不等于状态一致**，自身广播同样可触发 R2。

## 4. 本轮未解除问题与建议

无新增 BLOCKER。以下两项 MAJOR 为放行必修，属于 N2/N3 整改路径的残留问题。

### R1／MAJOR（N3 未闭合）：成功回调删除保存期间的新补丁，再次保存为空

**证据：** `src/App.tsx:981–1003`，尤其 :997；再次提交 :990–995；后端空 entries 仍成功返回 `src-tauri/src/lib.rs:68–91`。

确定性顺序：编辑 theme=dark → 提交，记录 seq=1 → 保存等待期间编辑 theme=light，patchSeq=2、Map 内更新为 light → 第一轮成功，无条件 clear 删除 light → 序号不同，界面提示“可再次保存”、dirty=true → 再次提交 entries=[] → 无新编辑，序号相同，界面提示“已保存”、dirty=false。后端 theme 仍 dark，草稿仍 light。无需同时写盘或 IPC 乱序；实际提取的 set/save 已在 Node 内确认 Map 被清空、第二轮提交 [] 并清 dirty。

**建议：** 成功仅移除本轮确已提交且之后未被改动的补丁，为每个路径记录编辑代次；保存期间更新的同一路径和新增路径必须保留。也可在提交时分离 in-flight/pending Map，失败再按代次合并。dirty 应由尚未提交补丁决定，不能单靠计数器后又全量 clear。定点验证同路径更新、新路径更新、失败后重试及重复保存单飞即可。

### R2／MAJOR（N2/N3 未闭合）：迟到重拉覆盖编辑；放弃未纳入保存状态机

**证据：** `src/App.tsx:957–970`（返回时仅检查 disposed）；:981–985 编辑递增；:1155–1160 放弃返回直接覆盖并 clear；:988–1008 仅保存受 savingRef 保护。

确定性顺序：设置页 clean → 收到配置广播，启动 get_config → 响应返回前用户编辑 theme=light，dirty=true、Map 有新补丁 → 原重拉响应返回旧/已持久化 theme=dark → setCfg 覆盖 light、setDirty(false)、clear Map。响应是否是最新后端配置都不影响“覆盖响应等待期间新草稿”的结论。实际提取 :963–968 回调在 Node 内已确认该状态转换。自身成功广播和他窗 chip 广播均可成为入口。

放弃也没有请求代次或编辑复核：等待 get_config 期间的新编辑会被迟到响应清掉。保存期间“提交 dark → 编辑 light → 放弃返回并清草稿 → 原保存成功”还会因 patchSeq 未复位/失效而重新设置 dirty=true，但 Map 已空，落入 R1 的空保存路径。仅设置 savingRef 不限制这些交叉。

**建议：** 为重拉和放弃建立请求/草稿代次；请求发出时记录编辑代次，返回时同时核对请求仍有效、代次未变及允许覆盖的状态，否则保留草稿并提示。明确保存中放弃的语义，可禁用放弃直至保存结束；放弃等待期间的新编辑不得被静默清除。同步更新 ref 或统一 reducer，避免事件读取与 Map/dirty 不一致。定点覆盖 clean 重拉中编辑、自身广播中编辑、放弃等待中编辑、保存中放弃即可。
